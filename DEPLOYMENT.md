# Доступ к роадмапе

GitHub Pages раздаёт публичную страницу входа. Данные загружаются только после
входа по логину и паролю через Supabase Auth. Разрешение проверяется в базе по
`roadmap_members`: одной регистрации в Supabase недостаточно.

## Заранее созданные логины

В `static/js/config.js` установлен `loginDomain: "roadmap.invalid"`.
Пользователь вводит короткий логин, а приложение дописывает технический домен
для обращения к Supabase Auth. Настоящая почта не нужна. Примеры аккаунтов:

| Логин на сайте | Email при создании в Supabase |
|---|---|
| `sgc` | `sgc@roadmap.invalid` |
| `ds` | `ds@roadmap.invalid` |
| `go` | `go@roadmap.invalid` |

В **Authentication → Users → Add user → Create new user** задайте соответствующий
технический email, пароль и включите **Auto Confirm User**. Каждый аккаунт
получает свою запись в `roadmap_members` по инструкции ниже. Используйте
создание с паролем: технические адреса не принимают приглашения и письма
восстановления. Пароль проверяет Supabase; приложение его не хранит.

Логины состоят из 1–32 латинских букв, цифр, точек, дефисов или подчёркиваний;
первый символ — буква или цифра. Регистр при входе приводится к нижнему.
Регистрацию и анонимный доступ включать не нужно. Новая миграция для логинов
не требуется.

Существующий адрес другого домена не переименовывается автоматически. Можно
настроить `loginDomain` под единый домен существующих аккаунтов; если удалить
параметр, страница снова принимает полные email. Смена интерфейса сама по себе
не исправляет `invalid_credentials`: пароль должен совпадать с заданным аккаунту.

## Порядок включения

1. В Supabase → Authentication → Sign In / Providers оставьте Email включённым,
   отключите **Allow new users to sign up** и Anonymous Sign-Ins.
2. В SQL Editor выполните миграцию
   `supabase/migrations/20261117_require_member_login.sql`.
   Она удаляет прежние политики трёх таблиц и запрещает анонимный доступ.
   Данные не удаляются. До выдачи разрешений роадмапа закрыта для всех.
3. В Authentication → Users → Add user → Create new user создайте пользователей
   с техническими email из раздела выше, паролем и включённым Auto Confirm User. Пароли вводите только
   в Supabase; не помещайте их в код, Git или SQL-файлы.
4. Выдайте доступ в SQL Editor для каждого созданного пользователя, подставив
   его UUID из Authentication → Users:

   ```sql
   insert into public.roadmap_members (roadmap_id, user_id)
   values ('main', '<UUID пользователя>')
   on conflict do nothing;
   ```

5. Опубликуйте обновлённый frontend в GitHub Pages после миграции.
   Если миграция разработчиков ещё не применена, сначала выполните также
   `supabase/migrations/20261113_add_developers.sql`.
6. В приватном окне проверьте: до входа видна только форма; неверный пароль
   не открывает данные; пользователь без записи в `roadmap_members` не получает
   роадмапу; разрешённый пользователь читает и сохраняет изменения; после
   выхода экран и данные очищаются. Проверьте, что запросы к обеим таблицам
   без access token не возвращают данные и не позволяют запись.

Для отзыва доступа удалите соответствующую строку из `roadmap_members` через
SQL Editor. Уже загруженные пользователем данные отозвать невозможно.

Сессия хранится только в sessionStorage вкладки. Данные роадмапы больше не
кешируются в localStorage; кеш старой версии очищается при запуске. Пароли
проверяет Supabase, приложение их не сохраняет. Публичный publishable key
не заменяет авторизацию: защиту обеспечивают grants и RLS на сервере.

## Индексация

`index.html` и `404.html` содержат `noindex`, а `robots.txt` запрещает обход
всего сайта. Это указания добросовестным поисковым роботам. Произвольный бот
может скачать публичную форму входа, но данные ему недоступны при применённой
миграции. Сам GitHub Pages не поддерживает HTTP Basic Auth и не может скрыть
статические файлы от запросов без дополнительного прокси или переноса.

Если сайт уже попал в поиск, удалите его URL через инструменты удаления
Google Search Console / Яндекс Вебмастера: `robots.txt` не удаляет старые
результаты, а запрет обхода мешает роботу увидеть новый `noindex`.
История публичного Git-репозитория также не становится закрытой от этих правок.

## Проверки локально

Node.js 26+ (либо поддерживаемые jsdom версии Node.js 22.22.2+ / 24.15.0+).
`npm install` → `npm test`.
Тесты используют локальные данные и имитацию Supabase, не изменяя рабочую базу.

## Интерфейс

Главный экран содержит диаграмму, фильтр команды, список разработчиков и
кнопку **↗ Связать проекты**. **+ Проект** открывает создание активности.
Меню **Ещё** содержит отпуск, настройки команды, обновление, импорт/экспорт и выход.

**Загрузка команд**, **Список проектов** и **Настройки плана** под диаграммой
свёрнуты по умолчанию и открываются нажатием на заголовок. Период и лимиты
меняются в **Настройках плана**. Подсказки и легенда цветов находятся в
**Как пользоваться** под диаграммой.

Календарь и имена разработчиков закреплены при прокрутке диаграммы.
Кнопки в строке и кнопка связи под проектом появляются при наведении или
переходе клавиатурного фокуса; на сенсорном экране они видны постоянно.
Действия над связью появляются при выборе стрелки. Уведомления об успешном
сохранении исчезают автоматически; ошибки остаются до закрытия или следующего действия.

## Команды и лимиты загрузки

DS и Go — отдельные команды одного домена. Роадмапа и связи между проектами
общие; бизнес- и технические слоты считаются отдельно для каждой команды.
В общем виде **Загрузка команд** показывает отдельные строки DS и Go,
а фильтр оставляет строки выбранной команды.

Для DS по умолчанию **3 бизнес-слота и 1 технический**. Для Go используются
прежние значения `business_slots` и `tech_slots`, они не сбрасываются.
Один слот, занятый несколькими разработчиками одной команды, считается один раз;
одинаковый слот у DS и Go учитывается независимо в обеих командах.
Активности без назначенной команды показываются без проверки лимита.
Скрытие строк и фильтр команды по-прежнему влияют на расчёт.
Учёт QA остаётся по именам QA среди видимых активностей.

Значения DS 3/1 работают и на прежней базе. Чтобы разрешить изменение этих
лимитов в **Настройках плана**, в **Supabase → SQL Editor → New query** выполните
[20261119_split_team_capacity.sql](supabase/migrations/20261119_split_team_capacity.sql)
и обновите страницу. Миграция добавляет `ds_business_slots` и `ds_tech_slots`,
сохраняет текущие лимиты Go и правила доступа. Повторное выполнение сохраняет
уже настроенные значения. До миграции поля DS недоступны для редактирования,
но период и лимиты Go можно менять.

Экспорт включает лимиты обеих команд. Старый JSON без лимитов DS импортируется
со значениями 3/1; импорт других значений DS в старую схему отклоняется до удаления данных.

## Порядок и видимость разработчиков

Над диаграммой откройте **Разработчики**: найдите человека через поиск и
включите или выключите переключатель. Список сгруппирован по DS / Go.
Имена скрытых появляются над диаграммой — нажмите на имя с **+**, чтобы вернуть
только этого человека. **Показать всех** в списке возвращает всех сразу.

При наведении на строку под именем разработчика доступны **↑ / ↓**, перетаскивание
за **⋮⋮** и **Скрыть**. Стрелки перемещают строку относительно ближайшей видимой
строки с учётом фильтра команды. **Вернуть всех** над диаграммой возвращает
все скрытые строки, сохраняя выбранный порядок.

В окне **Настройки команды** также доступны флажки видимости, перестановка строк и
редактирование имени/команды. Там порядок задаётся относительно полного списка.

Это общий вид: изменения сразу сохраняются в Supabase и синхронизируются у
участников. Скрытие действует на диаграмму, таблицу и расчёт загрузки;
активности остаются в базе и полном JSON-экспорте. Фильтр команды DS/Go
применяется дополнительно и остаётся личным фильтром текущей страницы.

Новая миграция не нужна: `hidden` и `order` хранятся внутри существующего JSON
`roadmap_settings.developers`. Старые записи без этих полей видны и изначально
сортируются по имени. При одновременных изменениях проверяется версия настроек;
при конфликте загружается актуальный список и предлагается повторить действие.

## Стрелки между проектами

Перед публикацией этой версии один раз выполните в Supabase:

1. Откройте **SQL Editor → New query**.
2. Скопируйте весь файл
   [20261119_add_activity_links.sql](supabase/migrations/20261119_add_activity_links.sql)
   и нажмите **Run**. Это добавляет поле для связей; аккаунты, данные и доступ не меняются.
3. После публикации frontend обновите страницу роадмапы.

До применения SQL роадмапа работает, но кнопка **↗ Связать проекты** недоступна.
Повторное выполнение SQL безопасно: сохранённые связи остаются на месте.

Наведите на проект и потяните круглую кнопку **↗ под проектом** к другому проекту. Цель подсветится
зелёным; отпустите кнопку мыши, чтобы сохранить связь. **Esc**, отмена жеста
или отпускание за пределами проекта не создают связь.

Можно также нажать **↗ Связать проекты → начальный проект → конечный проект**
или нажать кнопку ↗ под проектом, а затем выбрать цель.
Можно соединять DS → Go, Go → DS и другие проекты. Обратная стрелка создаётся
отдельно выбором проектов в обратном порядке. Отпуска в связях не участвуют.
**Esc** или **Отменить** отменяет выбор. Чтобы убрать связь, нажмите на стрелку,
затем **Удалить связь**. **⇄ Развернуть** меняет направление выбранной связи.
Если обратная связь уже существует, повтор не создаётся. Выбор проектов
и стрелок также доступен через Tab и Enter.

Линии имеют скруглённые углы и обходят карточки проектов. Цвет соответствует
команде разработчика исходного проекта: DS — фиолетовый, Go — бирюзовый.
При наведении на стрелку подсвечиваются оба связанных проекта.

Связи общие для команды. Стрелки следуют за проектами при переносе дат,
изменении длительности и перестановке разработчиков. Они обозначают связь,
но не изменяют сроки автоматически. Если один из проектов скрыт фильтром,
скрытием разработчика или горизонтом дат, стрелка не отображается; связь сохраняется.

Пары ID хранятся в `roadmap_settings.activity_links` и используют существующие
RLS, проверку версии настроек и realtime. Удалённые проекты не отображаются
в связях и не экспортируются как их участники; устаревшие ссылки очищаются
при следующем сохранении связей. Экспорт содержит связи скрытых проектов.
При импорте выдаются новые ID активностей, и связи переназначаются на них.
Некорректные связи в JSON отклоняются до удаления данных в облаке.
